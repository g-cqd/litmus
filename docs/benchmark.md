# Benchmark

`bench/` compares the Swift mutation-testing tools on one subject and exercises every Litmus feature on it. The
subject is original to this repository. Its structure is inspired by [j-khn/mutation-test-ios-app]: an iOS app with
local packages, run by several tools. Its code is not copied.

[j-khn/mutation-test-ios-app]: https://github.com/j-khn/mutation-test-ios-app

## The subject: `bench/Transit`

A transit-fares iOS 17 app: a SwiftUI trip screen over three local packages, built by `Transit.xcworkspace`
(`Transit.xcodeproj` is generated by `xcodegen` from `project.yml`).

| Part | Tests | What it puts in the way of a mutation tester |
| --- | --- | --- |
| `Modules/FareKit` (zones, concessions, peak surcharge, rounding, daily cap, transfers) | Swift Testing, parameterised | plain logic, boundaries |
| `Modules/TripKit` (journeys, connections, delay propagation) | Swift Testing and XCTest | kills only XCTest sees; a loop that a mutant makes endless (timeouts); an index that a mutant makes trap (crashes) |
| `Modules/WalletKit` (balance, limits, audit trail, points) | Swift Testing | a `static let` and a `lazy var` evaluated once per process; global state a mutant can leave behind; a lock whose removal deadlocks; equivalent mutants (`clampedPercent`) |
| `App` (view model and SwiftUI views) | `TransitTests` (hosted, in the scheme), `TransitExtraTests` (hosted, **not** in the scheme), `TransitUITests` | app-hosted tests; a test target the scheme leaves out; view mutants only UI tests see |

The `Transit` scheme tests `TransitTests` and the three package test targets: 29 Swift Testing tests and 5 XCTest
cases, deterministic (twenty consecutive runs of every suite pass).

## Tools

Every tool runs from the **latest release binary** its project publishes on GitHub; nothing is built.
`bench/install-tools.sh` asks the GitHub API for each latest release, downloads the macOS archive into a prefix (never
system-wide), checks it against the release's published `.sha256` when there is one, and records the archive's SHA-256
otherwise. `<prefix>/versions.tsv` lists tool, release tag, asset, SHA-256 and how it was checked; the workflow shows
that table in its summary.

| Id | Tool | Release binary | Checksum |
| --- | --- | --- | --- |
| `litmus` | Litmus (this repository) | `litmus-<version>-macos-arm64.tar.gz` | published `.sha256` |
| `smt` | [ericodx/swift-mutation-testing] | `swift-mutation-testing-<version>-macos.tar.gz` | recorded |
| `muter` | [Muter] | `muter-<version>-macos-universal.tar.gz` | published `.sha256` |
| `xcmutate` | [RyoHirota68/xcmutate] | `xcmutate-<version>-macos-universal.tar.gz` | published `.sha256` |
| `dlitmus` | [debugholic/litmus] | `litmus-<version>-macos-universal.tar.gz` | recorded |
| `mutest` | [j-khn/mutest-swift] | none: source archives only | skipped |

[ericodx/swift-mutation-testing]: https://github.com/ericodx/swift-mutation-testing
[Muter]: https://github.com/muter-mutation-testing/muter
[RyoHirota68/xcmutate]: https://github.com/RyoHirota68/xcmutate
[debugholic/litmus]: https://github.com/debugholic/litmus
[j-khn/mutest-swift]: https://github.com/j-khn/mutest-swift

mutest-swift keeps its adapter: it runs as soon as a release ships a macOS binary. Of the tools xcmutate's README credits,
[mizchi/mutator] is not here: it mutation-tests TypeScript under Vitest and cannot run on a Swift subject.

[mizchi/mutator]: https://github.com/mizchi/mutator

The runner only uses the paths in `LITMUS_BIN`, `SMT_BIN`, `MUTER_BIN`, `XCMUTATE_BIN`, `DLITMUS_BIN` and `MUTEST_BIN`
(failing those, `litmus`, `swift-mutation-testing`, `muter` and `xcmutate` on `PATH`). debugholic's executable is also
named `litmus`, and mutest-swift's `swift-mutation-testing`, so only their variables name them.

Litmus and swift-mutation-testing run with `--operator-tier experimental`, their broadest set; the others run their
default operators. The sets still differ, so compare counts and scores within a scenario with care. debugholic/litmus
reports no replacement text, only a description ("changed > to <="); probes read their spellings from it.

## Scenarios

`python3 bench/run.py --list` prints them.

| Id | Tools | What it runs |
| --- | --- | --- |
| `ios-app` | all | the whole workspace on a simulator |
| `package` | all | `WalletKit` on macOS (SwiftPM) |
| `diff` | all | a commit that rewrites two lines of `Fare.swift`: Litmus `--diff-base`, xcmutate and debugholic/litmus `--since`, mutest-swift `--source-commit`; swift-mutation-testing and Muter, which have no diff mode, get the changed file |
| `reach-off` | Litmus | `ios-app` with `--no-per-test-reach` |
| `shared-process` | Litmus | `WalletKit` isolated, then with `--shared-process on`; the note counts differing verdicts |
| `test-changes` | Litmus | a nightly run of `FareKit`, then a commit that only weakens a test, with `--include-test-changes --reach-from` |
| `all-targets` | Litmus | `--all-test-targets --skip-failing-targets` with a failing test added to the target the scheme leaves out |
| `ui-tests` | Litmus | `remove-view-element` mutants with `--all-test-targets --include-ui-tests` |
| `inner-loop` | Litmus | `accept` of the equivalent mutant, a run without it, `--only-id` on a survivor, `analyze --format agent`, `--verify-accepted` |
| `reuse` | Litmus | `FareKit` twice with one `--result-store` |
| `shards` | Litmus | `TripKit` as `--shard 1/2` and `2/2`, then `merge` |
| `budget` | Litmus | `ios-app` with `--budget 60` |

Every cell runs on a fresh git copy of the subject in a temporary directory, so no tool sees another's caches or
edits. Locally, `--jobs N` runs N cells at once. SwiftPM cells run in parallel. Simulator cells run one at a time,
because they share the simulator, and they start first so the macOS cells fill the time beside them. Each step's CPU
time comes from its own child's resource usage (`wait4`), so cells running at once never count each other's time.
Wall times of parallel cells still compete for the machine: for comparable timings, use `--jobs 1` or the workflow.

## Time limits

A step ends when it has shown no activity for `--idle-timeout` seconds (default 600), or after `--hard-timeout`
seconds (default 5400) regardless. Activity is any of:

- bytes on its standard output or error;
- more than 0.5 s of new CPU time in its process group (`ps`), which catches a test run that prints nothing;
- a newer modification time under its output directory or the cell's directory.

A slow tool that is still working is never ended by the idle limit; a hung one is. The runner starts each step in its
own process group and ends the whole group (SIGTERM, then SIGKILL after 15 s), and it ends the running group if it is
itself interrupted.

## Results

`bench/results/<UTC time>/` (or `--output`) holds `results.json`, `results.md` and every step's log under
`<tool>/<scenario>/`. `results.md` reads top to bottom:

1. **Score card**: one row per tool. It shows scenarios that ran cleanly, probes judged right, false kills, false
   survivors, probes mutated, `package` and `ios-app` wall times, and peak memory and disk.
2. **Correctness**: the probe table (below), one column per tool. It also reports any verdict that differs between
   Litmus's isolated and shared-process modes.
3. **Completeness**: per scenario and tool, the status, the mutants reported and the score.
4. **Speed**: per scenario and tool, the wall time of the whole cell and the seconds per decided mutant.
5. **Resources**: per scenario and tool, CPU time, peak memory and peak disk.
6. **Verdicts** (every count) and **Notes** (scenario notes, and the first error lines of a failed row).

### Probes: what correctness means here

Tools mutate different sites and spell mutations differently, so their scores are not directly comparable.
`bench/probes.json` names mutants of the subject whose right verdict is known:

- an endless loop, which must time out;
- an out-of-range index, which must trap;
- a boundary only an XCTest case checks;
- the `static let`;
- a surcharge condition;
- two equivalent clamps, which must survive;
- a boundary no test checks, which must survive.

A probe matches a tool's mutant on the same file and line (found by an anchor text, so the probes follow edits to
the subject) whose replacement contains one of the probe's spellings.

| Outcome | Meaning |
| --- | --- |
| ✅ | the verdict is the expected one (detected: killed, timed out or crashed; undetected: survived or no coverage) |
| ❌ false kill | a mutant that must survive was reported detected |
| ❌ false survivor | a mutant that must be detected was reported undetected |
| ❔ undecided | unviable, ignored or another status |
| ⚠️ not mutated | the tool mutated the probe's file, not that site: a completeness gap |
| – | the scenario never touched the probe's file |

A wrong verdict in any scenario counts against the tool. Rows keep their mutants, so `--merge` re-evaluates the
probes with the `probes.json` it runs with.

### Measures

| Measure | How |
| --- | --- |
| Status | `ok` when the report was read and no step timed out; a non-zero exit is often a finding (survivors, a gate) |
| Score | (killed + timeout + crashed) / (that + survived + no coverage), the same formula for every tool |
| Wall time | the whole cell, every step included |
| CPU time | `wait4` of each step's own child: every process it waited for, whatever ran beside it |
| Peak memory | the largest resident set among those processes (`ru_maxrss`) |
| Peak disk | `du` of the subject copy, the cell's private `TMPDIR` and its output, sampled every 30 s |

`run.py` exits non-zero, and a CI cell fails, only when the benchmark did not happen (a tool's binary is missing) or Litmus's own cell did not end `ok`. Another tool that fails, times out or writes no report is a result: its row says so, with its first errors. For example, Muter 17 on WalletKit fails because its instrumented `Wallet.swift` does not compile (`attribute 'public' can only be used…`).

Each cell gets its own `TMPDIR`, so a tool's sandboxes there count as its disk use and are removed with the cell, and
xcmutate's `--work-dir` is put inside the cell. Not counted: Xcode's default DerivedData, which tools that do not choose
their own build into, and debugholic/litmus's work copies in `~/Library/Caches/litmus`.

## Running

```sh
eval "$(bench/install-tools.sh)"                        # the latest release binary of every tool
python3 bench/run.py --jobs 4                           # every tool, every scenario
python3 bench/run.py --tools litmus,smt --scenarios package,diff --simulator "iPhone 17 Pro"
```

`bench/run.py` is formatted and linted with Ruff (`bench/ruff.toml`): `ruff format bench && ruff check bench`.

Do not export `TOOLCHAINS` for the run: xcodebuild then links the local packages' manifests with that toolchain and
fails to resolve them.

On GitHub, the **Benchmark** workflow (`.github/workflows/bench.yml`) runs weekly (Mondays, 04:17 UTC, every tool and
scenario) and on demand, and parallelises the whole matrix:

1. `plan` lists the applicable tool × scenario cells (`bench/run.py --matrix`).
2. `prepare` downloads the latest release binary of every tool once, on Linux, into one archive (nothing is built).
3. One `cell` job per cell, each on its own macOS runner (so simulator cells never share a simulator), up to the
   `max-parallel` input at once.
4. `summary` merges every cell's `results.json` (`bench/run.py --merge`) into the run's summary and a `bench-summary`
   artifact.

On demand, the inputs choose the tools, the scenarios, both time limits, the parallelism and the runner label; the
weekly run takes the defaults.
