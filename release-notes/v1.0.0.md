## Behaviour

- `litmus mcp`:
  - Newline-delimited JSON-RPC 2.0, served in order, with `initialize`, `ping`, `tools/list` and `tools/call`. A failing tool answers with `isError: true`, not a protocol error.
  - Each tool runs the matching subcommand of the same executable, so it validates input and needs consent exactly as the command line does. `litmus_run` refuses to run unless `trust_project` is `true`.
  - `litmus_run` keeps a build directory and result store per subject under `~/Library/Caches/litmus/mcp/`. Measured on the `Example` fixture: a repeated run reused all 4 verdicts in 0.2 s.
  - Not included: test processes kept alive between calls.
- `litmus watch`:
  - Checks the subject's Swift files every `--interval` seconds, outside `.build`, `.git`, `DerivedData`, `.swiftpm` and `node_modules`. After a quiet interval it runs `litmus run --diff-base <base> --include-test-changes --background`, with a persistent build directory and result store per subject.
  - Each pass prints the verdicts that changed since the previous one, and the mutants left undetected.
- `docs/formal/` states three properties with their assumptions, arguments from the code, and the tests that check them:
  - workspace restoration after a crash or cancellation;
  - soundness of closure-keyed reuse;
  - equal verdicts with and without shared processes and UI sessions.

  These are written arguments, not machine-checked proofs.
- `docs/stability.md` is binding from 1.0: subcommands, flags, exit codes, `.litmus.json`, `.litmus-accepted.json`, baselines, `run.json`/`run.pb`, the JSON, agent, SARIF and Stryker reports, the store format, and the MCP tools change incompatibly only in a new major version. The `github-summary` and `html` formats are for people and may change in any minor version.
