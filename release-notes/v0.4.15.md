# litmus 0.4.15 (from 0.4.14)

Fixes from checking 0.4.14 on a real multi-project workspace. The simulator helper counts XCTest cases again under per-test reach, which has been on by default since 0.4.14. `--skip-failing-targets` works under `xcodebuild` and after a helper fallback. `--all-test-targets` on a workspace tests the projects the workspace lists. `--reach-from` and `--baseline-run` accept a run directory. Builds on analyzerkit's new `XcodeWorkspace`.

## Behaviour

- **Simulator helper (regression in 0.4.14).** With per-test reach, the helper wrote its XCTest results next to the reach FIFO instead of next to the events log, so Litmus never saw them. A bundle with only XCTest cases counted no tests. Its baseline then read "the simulator helper ran no test", and the run fell back to `xcodebuild` (slower, same verdicts). An XCTest failure under the helper was reported as a crash. The helper now receives its XCTest results file as a separate argument. On a two-project workspace fixture, the run takes 25 s instead of 91 s.
- **`--skip-failing-targets` under `xcodebuild`.** The target to quarantine is the first failure the result bundle's summary names, or else a bundle with failed tests. Before, the quarantine loop found no failed target, and the run stopped at the baseline.
- **`--skip-failing-targets` with the simulator helper.** When the helper's baseline fails, Litmus falls back to `xcodebuild` and quarantines there. It then retries the helper without the quarantined targets and goes back to the helper if that retry passes. A target that fails only under the helper keeps the run on `xcodebuild`.
- **`--all-test-targets` on an `.xcworkspace`.** The scheme tests the unit-test targets of the projects that `contents.xcworkspacedata` lists: `group:` locations through nested groups, plus `container:` and `absolute:` locations. Before, it tested every `.xcodeproj` found under the repository. Listed projects outside the copied root are left out, with a note.
- **Not-run summary.** When the only targets covering some mutants failed unmutated, the CLI now says so (`only test targets that failed unmutated cover them`) instead of `the failing-test-target limit was reached`.
- **Read errors.** When `--reach-from` or `--baseline-run` cannot be read, the error names the option and the file.

## Verified on a simulator (iPhone 18 Pro, iOS 27.2)

- A workspace with an app project and a framework project, plus an unlisted project whose test always fails. Both mutants were killed through the helper.
- The same workspace with the failing project listed:
  - with the helper and with `--no-simulator-helper`, the failing target is quarantined, both mutants are killed, and the run exits 0;
  - with the helper, the run goes back to the helper after the quarantine;
  - the mutant only the quarantined target covers is `notRun` (`stoppedBy: failing-test-target`).
- `ExampleApp` with its own scheme stays on the helper. Every verdict kind still appears.
