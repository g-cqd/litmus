# 2026-11-02 (07) — the family train, and what it broke on the way

All 21 upstream items were implemented (aemi ADR 0028, analyzerkit ADR-0030, AemiJSON diary) and adopted (ADR 0006).
The six analyzers build and pass their tests on the new revisions (arcleak 231, deadwood 406, dolly 211, fcheck 152,
modeler 112, swift-search 69). aemi 1095 tests, AemiRegex 177, AemiJSON 509, AemiProtobuf 370, analyzerkit 390 and
Litmus 54 pass; the touched aemi and analyzerkit suites also pass on Linux (swift:6.4 container).

What went wrong, in order:

- **The disk filled.** Six consumer copies and two Linux build directories brought the data volume to 825 MB; a smoke
  build failed with ENOSPC. Copies are now deleted after each check.
- **The session cleanup killed a `swift build`** (status 137, no output) three seconds after a timed-out test run
  ended: the run's session id had become a new build's. Fixed upstream with a rule and three tests (ADR 0006).
- **My own interruption test was wrong.** `cd /tmp && litmus … &` backgrounds a subshell; `$!` was bash, so SIGTERM
  "killed Litmus" in 0 s and SIGINT "was ignored". lldb on the real pid (`sigaction(15)` = `SIG_IGN`) and a breakpoint on
  `sigaction` showed `TerminationSignals` working. With the right pid: exit 130 and 143, checkpoint incomplete, nothing
  left. The smoke script now checks it, with `$!` of the command itself.

Checked that had not been: the watchdog costs 1.3 ms a sample and nothing measurable on a 1.5–2.5 s child; the
parallelization width works under `swiftpm-testing-helper` and is expensive (decision 5); the compiler's
`-print-static-build-config` has no `canImport`, answered from the SDK's modules instead; swift-service-lifecycle's
`UnixSignals` does not restore dispositions, ours does.
